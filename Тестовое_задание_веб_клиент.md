Тестовое задание: веб-клиент образовательного ИИ-агента

Контекст

Мы разрабатываем LOM AI — образовательную платформу с ИИ-инструментами для школьников и преподавателей.

В рамках тестового задания предлагаем реализовать небольшой самостоятельный веб-клиент для взаимодействия школьника с ИИ-агентом.

Основная цель задания — посмотреть, как вы проектируете и реализуете frontend-приложение: структуру компонентов, управление состоянием, работу с асинхронными событиями, UX и обработку нестандартных состояний.

Подключать настоящий LLM или внешний AI API не требуется. Поведение агента необходимо имитировать локально.

Что нужно реализовать

Представьте, что вы разрабатываете первую версию интерфейса LOM AI, в которой школьник может обратиться к ИИ за помощью с учебной задачей.

Например:

«Объясни мне закон Ома простыми словами»

или

«Помоги решить эту задачу по математике, но не давай ответ сразу».

Необходимо реализовать работающий интерфейс чата с mock AI-agent.

1. Чат с ИИ

Пользователь должен иметь возможность:

- написать сообщение;

- отправить его агенту;

- увидеть ответ;

- продолжить диалог несколькими сообщениями.

Ответы агента должны хотя бы в некоторых случаях зависеть от предыдущих сообщений.

Например:

Пользователь:

Объясни второй закон Ньютона.

Агент:

Второй закон Ньютона связывает силу, массу и ускорение...

Пользователь:

А теперь объясни проще.

Второй ответ агента должен учитывать, что пользователь просит упростить предыдущее объяснение.

Не требуется реализовывать сложную LLM-логику. Достаточно нескольких разумных сценариев.

2. Имитация streaming

Ответ агента должен появляться постепенно, а не сразу целиком.

Например, mock-agent может:

- сначала перейти в состояние обработки запроса;

- через небольшую задержку начать выдавать ответ;

- добавлять текст небольшими фрагментами;

- завершить генерацию.

Настоящий LLM API для этого использовать не нужно.

Нам важно посмотреть, как frontend работает с асинхронным обновлением состояния и отображением постепенно приходящих данных.

3. Состояния работы агента

ИИ-агенты могут выполнять запрос заметно дольше обычного HTTP-запроса, обращаться к инструментам и проходить несколько этапов выполнения задачи.

Интерфейс должен понятно обрабатывать хотя бы следующие состояния:

- запрос отправлен;

- агент обрабатывает запрос;

- приходит ответ;

- запрос успешно завершён;

- произошла ошибка.

Дополнительно реализуйте хотя бы один сценарий, в котором агент использует условный инструмент.

Например:

Пользователь: «Сколько будет 17 × 24?»

Агент может последовательно сгенерировать события:

- обработка запроса;

- вызов инструмента calculator;

- получение результата инструмента;

- формирование ответа;

- streaming ответа пользователю.

Сам инструмент может быть полностью mock-реализацией.

Вы самостоятельно решаете:

- какие технические состояния стоит показывать пользователю;

- как визуально отображать работу агента;

- какую информацию лучше скрыть как внутреннюю.

Не требуется отображать внутреннюю цепочку рассуждений модели (chain of thought). Если вы хотите показать процесс работы агента, используйте высокоуровневые статусы вроде «Анализирую задачу», «Использую калькулятор», «Формирую ответ».

4. Mock AI-agent

Для задания необходимо самостоятельно реализовать небольшую имитацию AI-agent.

Для этого не нужен отдельный backend: mock может находиться непосредственно в приложении.

Он должен:

- принимать сообщение пользователя и историю текущего диалога;

- с небольшой искусственной задержкой возвращать ответ;

- поддерживать постепенную выдачу ответа;

- иметь несколько вариантов поведения;

- хотя бы в одном сценарии учитывать предыдущие сообщения;

- хотя бы в одном сценарии имитировать использование инструмента;

- позволять продемонстрировать ошибку или неуспешное выполнение запроса.

Например, внутри приложения взаимодействие с агентом можно представить как последовательность событий:

type AgentEvent =| { type:"started" }| { type:"status"; message:string }| { type:"tool_call"; tool:string }| { type:"tool_result"; tool:string; result:string }| { type:"text_delta"; text:string }| { type:"completed" }| { type:"error"; message:string };

Использовать именно этот контракт не обязательно. Это только пример.

Вы можете выбрать другую архитектуру, если считаете её более подходящей.

5. Несколько диалогов

Нужно реализовать минимальное управление чатами:

- создание нового диалога;

- переключение между существующими диалогами;

- отображение истории сообщений после переключения.

Не требуется полноценная авторизация или серверное хранение пользовательских аккаунтов.

Допустимо использовать локальное хранение состояния, если вы считаете это разумным для тестового проекта.

6. Базовый UX

Интерфейс должен быть пригоден для реального использования.

Мы ожидаем наличие и нормальную обработку:

- пустого состояния;

- loading-состояний;

- ошибок;

- длинных сообщений;

- повторной отправки сообщения после ошибки;

- действий пользователя во время генерации ответа;

- переключения между диалогами.

Например, подумайте:

- можно ли отправить второе сообщение, пока агент отвечает на первое;

- что произойдёт, если в этот момент переключиться на другой чат;

- можно ли повторить запрос после ошибки;

- сохраняется ли незавершённое состояние разных диалогов корректно.

Мы не задаём конкретное поведение — нам интересно ваше решение.

Интерфейс должен нормально выглядеть как минимум на обычном desktop-экране.

Адаптивность для мобильных устройств будет плюсом.

Технологии

Вы можете самостоятельно выбрать frontend-стек.

Для проекта такого типа мы ожидаем современный компонентный frontend и использование TypeScript.

Например:

- React;

- Next.js;

- Vue/Nuxt;

- другой сопоставимый стек.

Выбор конкретной библиотеки UI, state management и остальных инструментов остаётся за вами.

Нам важнее качество архитектурных решений и реализации, чем использование конкретного фреймворка.

Дизайн

Готового макета нет.

Не требуется создавать сложный визуальный дизайн с нуля, но интерфейс должен быть аккуратным и понятным.

Можно использовать:

- готовые UI-библиотеки;

- собственные компоненты;

- AI-инструменты;

- существующие паттерны интерфейсов AI-чатов.

Представьте, что этим интерфейсом действительно будет пользоваться школьник.

При проектировании подумайте:

- какая информация ему действительно нужна;

- как понятно показать длительную работу агента;

- как отображать ошибки;

- какую техническую информацию лучше не показывать пользователю.

Использование AI-инструментов

Использование AI-инструментов разрешено и приветствуется.

В реальной работе мы сами активно используем современные AI-инструменты, поэтому не хотим искусственно запрещать их в тестовом задании.

При этом нам важно, чтобы разработчик:

- понимал сгенерированный код;

- мог оценивать корректность предложенных решений;

- замечал ошибки моделей;

- мог самостоятельно изменить или отладить решение;

- принимал архитектурные решения сам, а не автоматически соглашался с предложением модели.

В README добавьте небольшой раздел «Использование AI-инструментов»:

- какие инструменты вы использовали;

- для каких частей работы;

- приведите 1–2 примера, когда вам пришлось изменить, исправить или отклонить предложенное AI решение.

Полные логи общения или промпты присылать не нужно.

Что нужно прислать

1. Репозиторий с исходным кодом

В репозитории должен находиться весь код, необходимый для запуска проекта.

2. README

Кратко опишите:

- как запустить проект;

- используемый стек;

- структуру приложения;

- как организовано состояние приложения и диалогов;

- как реализованы streaming и события mock-agent;

- ключевые архитектурные решения;

- известные ограничения;

- что бы вы улучшили или переработали, если бы продолжали разработку.

README не должен быть большим — нам важно понять ход технических решений.

3. Короткая демонстрация

Приложите ссылку на короткую запись экрана или другой удобный способ посмотреть работу приложения без необходимости сразу запускать проект локально.

На что мы будем смотреть

В первую очередь нас интересуют:

- организация frontend-кода;

- архитектура компонентов;

- управление состоянием;

- работа с асинхронными событиями;

- корректность поведения интерфейса в разных состояниях;

- UX;

- качество и читаемость TypeScript-кода;

- самостоятельность принятых решений;

- способность объяснить эти решения;

- осознанное использование AI-инструментов.

Сложность mock-agent и количество реализованных сценариев сами по себе преимуществом не являются.

Что НЕ нужно делать

Чтобы тестовое не разрасталось, не требуется:

- подключать настоящий LLM;

- получать или покупать API-ключи;

- использовать внешние AI API;

- реализовывать отдельный полноценный backend;

- реализовывать сложную логику mock-agent;

- регистрация и авторизация пользователей;

- роли ученика/учителя/администратора;

- база данных пользователей;

- административная панель;

- pixel-perfect дизайн;

- сложная система предметов и учебных курсов;

- production deployment.

Лучше хорошо реализовать небольшой scope, чем добавить большое количество недоработанных функций.
