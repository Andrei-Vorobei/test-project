# Руководство по проекту LOM AI

Подробное описание того, как устроен и работает учебный чат-клиент. README — краткая витрина проекта, здесь — разбор «изнутри».

## 1. Что это

Веб-клиент чата с локальным имитируемым ИИ-агентом («помощник в учёбе»). Бэкенда, реальной LLM, API-ключей и авторизации нет: ответы генерирует модуль `mockAgent.ts` в браузере.

Стек: React 19, TypeScript, Vite, Redux Toolkit, Vitest. Включён React Compiler, поэтому ручной `useMemo`/`useCallback` почти не нужен.

Команды: `npm run dev` (запуск), `npm run build` (проверка типов и сборка), `npm run lint`, `npm test`.

Структура вдохновлена FSD, но упрощена: `app` — инфраструктура приложения, `features/chat` — всё про чат.

## 3. Пользовательские сценарии

1. **Первый запуск.** Диалогов нет, показывается приветствие и три кнопки-подсказки. Клик по подсказке отправляет её как сообщение.
2. **Новый диалог.** Кнопка «Новый диалог» создаёт чат и делает его активным. Новые чаты добавляются в начало списка (новые сверху).
3. **Отправка сообщения.** Если активного чата нет, он создаётся автоматически. Название диалога берётся из первого сообщения (до 36 символов, с «…»).
4. **Ответ агента.** Сначала индикатор «Обрабатываю запрос», затем текст появляется по кускам (стриминг), статус «Формирую ответ», в конце сообщение получает статус `complete`.
5. **Инструмент.** Запрос с арифметикой вызывает «Калькулятор»: показывается карточка вызова, затем результат, затем текст ответа.
6. **Ошибка и повтор.** Агент может вернуть ошибку; под сообщением блок с текстом ошибки и кнопкой «Попробовать ещё раз». Повтор не дублирует сообщение пользователя — старый ответ с ошибкой заменяется новым.
7. **Переключение чатов.** История каждого чата сохраняется. Генерация в другом чате продолжается в фоне.
8. **Удаление.** Иконка корзины в строке диалога, подтверждение через `window.confirm`. После удаления активным становится соседний чат (следующий, иначе предыдущий), иначе — пустое состояние. Незавершённая генерация удалённого чата отбрасывается.
9. **Перезагрузка.** Диалоги восстанавливаются из `localStorage`. Если ответ был прерван на середине, он превращается в ошибку с возможностью повторить.
10. **Поле ввода.** Enter — отправить, Shift+Enter — новая строка, ввод через IME учитывается. Высота растёт до 160 px, затем появляется внутренний скролл. Пока идёт генерация в активном чате, отправка заблокирована.

## 4. Что можно спросить у агента

| Запрос (пример)                                                                                                      | Сценарий                                                                                                                                                                                     |
| -------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| «Объясни закон Ома»                                                                                             | Объяснение закона Ома                                                                                                                                                             |
| «Объясни второй закон Ньютона»                                                                        | Объяснение закона Ньютона                                                                                                                                                     |
| «Помоги решить задачу, не давай ответ» (`реши задачу`, `с подсказкой`)  | Режим подсказок без готового ответа                                                                                                                                   |
| «Объясни проще» (`проще`, `короче`, `другими словами`)                              | **Учитывает историю**: берёт последний завершённый ответ ассистента; для закона Ома — упрощённый вариант |
| «Сколько будет 17 × 24?» (`+ - * × x / ÷`, запятая как десятичный разделитель) | Вызов инструмента «Калькулятор»                                                                                                                                         |
| «Вызови ошибку» (`смоделируй ошибку`, `ошибка агента`)                             | Событие `error`, затем повтор                                                                                                                                                    |
| Любой другой текст                                                                                               | Универсальный ответ с уточняющим вопросом                                                                                                                       |

Порядок проверки в агенте: ошибка → калькулятор → контекстное «проще» → закон Ома → закон Ньютона → задача → общий ответ.

## 4.1. Сценарии для демонстрации проекта

Ниже приведён короткий сценарий демонстрации, который последовательно показывает основные возможности приложения. Перед началом запустите проект командой `npm run dev` и откройте адрес, который напечатает Vite.

### Сценарий 1. Первый запуск и отправка сообщения

1. Откройте приложение в чистом состоянии.
2. Убедитесь, что отображается пустой экран чата с приветствием и подсказками.
3. Нажмите подсказку или введите `Объясни закон Ома`.
4. Покажите, что пользовательское сообщение появляется сразу, а ответ ассистента приходит постепенно.
5. Обратите внимание на статус генерации в шапке и на то, что поле ввода временно заблокировано.

Ожидаемый результат: приложение автоматически создаёт диалог, сохраняет оба сообщения и после завершения показывает готовый ответ.

### Сценарий 2. Контекст предыдущего ответа

1. В том же диалоге отправьте `Объясни закон Ома`.
2. После завершения ответа отправьте `Попроще` или `Объясни другими словами`.
3. Сравните второй ответ с первым.

Ожидаемый результат: агент использует последнее завершённое сообщение ассистента. Для закона Ома он выдаёт отдельное простое объяснение, а не обрабатывает запрос как независимый вопрос.

### Сценарий 3. Использование инструмента-калькулятора

1. Отправьте `Сколько будет 17 × 24?`.
2. Во время ответа покажите статус использования калькулятора.
3. Дождитесь карточки вызова инструмента и результата `17 × 24 = 408`.
4. Покажите итоговый текстовый ответ ассистента.

Ожидаемый результат: в сообщении видна последовательность `tool_call` → `tool_result`, а результат инструмента сохраняется в истории после завершения генерации.

Можно также проверить другие формы записи: `12,5 + 2`, `10 / 4`, `8 ÷ 2` или `7 x 6`.

### Сценарий 4. Ошибка и повторная попытка

1. Отправьте `Вызови ошибку` (также подходят `смоделируй ошибку` и `ошибка агента`).
2. Дождитесь состояния ошибки.
3. Убедитесь, что сообщение пользователя осталось в истории, а интерфейс показывает кнопку повторной попытки.
4. Нажмите повтор.

Ожидаемый результат: ошибка отображается явно, после retry создаётся новая попытка ответа без дублирования пользовательского сообщения. Это демонстрирует обработку неуспешного запроса.

### Сценарий 5. Несколько диалогов

1. Создайте новый диалог кнопкой `Новый диалог`.
2. Отправьте в нём другой вопрос, например `Второй закон Ньютона`.
3. Переключитесь между двумя диалогами через боковую панель.

Ожидаемый результат: каждый диалог сохраняет собственную историю, а активный чат меняется без смешивания сообщений.

### Сценарий 6. Переключение во время генерации

1. Отправьте длинный вопрос и сразу, пока ответ ещё печатается, откройте другой диалог.
2. Понаблюдайте за активным чатом и вернитесь к исходному диалогу после завершения генерации.

Ожидаемый результат: потоковые события остаются привязанными к диалогу и конкретному `requestId`. Ответ не появляется в другом чате и не повреждается при переключении.

### Сценарий 7. Удаление диалога

1. Создайте два диалога.
2. Удалите активный диалог.
3. Подтвердите действие в системном окне.
4. Повторите удаление и отмените его.

Ожидаемый результат: после подтверждения история удаляется, а приложение выбирает другой доступный диалог. При отмене ничего не меняется.

### Сценарий 8. Сохранение и восстановление

1. Создайте сообщение и дождитесь завершения ответа.
2. Обновите страницу браузера.
3. Проверьте, что список диалогов и история восстановились.

Ожидаемый результат: данные загружаются из `localStorage`. Если обновить страницу во время незавершённого ответа, такой ответ восстанавливается как прерванный и становится доступен для retry.

### Сценарий 9. Адаптивный интерфейс

1. Откройте DevTools и включите ширину около `390px`.
2. Проверьте открытие и закрытие боковой панели через кнопку меню.
3. Отправьте длинное сообщение и убедитесь, что страница не получает горизонтальную прокрутку.
4. Проверьте, что кнопка удаления остаётся доступной на сенсорном экране.

Ожидаемый результат: основные действия доступны на мобильной ширине, длинный текст переносится, а элементы управления не выходят за границы экрана.

## 5. Модель данных (`chatTypes.ts`)

- `Conversation`: `id`, `title`, `createdAt`, `updatedAt`, `messages[]`.
- `UserMessage`: `role: 'user'`, `content`, `createdAt`.
- `AssistantMessage`: `role: 'assistant'`, `content`, `status` (`processing | streaming | complete | error`), `userMessageId` (на какой вопрос отвечает), `errorMessage?`, `toolActivity?` (`{ name, result }`).
- `AgentGeneration` — живое состояние генерации: `requestId`, `assistantMessageId`, `statusText`, `tool`.

## 6. Состояние Redux (`chatsSlice.ts`)

```
chats: {
  conversations: Conversation[]
  activeConversationId: string | null
  persistenceWarning: string | null
  generations: Record<conversationId, AgentGeneration | undefined>   // не сохраняется
}
```

Редьюсеры: `createConversation`, `selectConversation`, `deleteConversation`, `setPersistenceWarning`.

### Thunk `runAssistant`

1. `condition` не даёт запустить вторую генерацию в том же чате, продублировать сообщение пользователя или повторить ответ, у которого нет ошибки.
2. `pending`: добавляет сообщение пользователя (или при повторе удаляет прежний ответ с ошибкой), добавляет пустое сообщение ассистента со статусом `processing`, создаёт запись в `generations` с `requestId` thunk-а.
3. Thunk читает события из `streamAgentReply` и диспатчит `agentEventReceived({ conversationId, requestId, event })`.
4. `completed` → `fulfilled`: статус `complete`, запись из `generations` удаляется.
5. `error` → `rejectWithValue(message)` → `rejected`: статус `error`, `errorMessage` сохраняется.

### Обработка событий

| Событие  | Эффект                                                                                                                        |
| --------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| `started`     | статус «Обрабатываю запрос»                                                                                |
| `status`      | `statusText` = текст события                                                                                          |
| `tool_call`   | создаётся `toolActivity` без результата                                                                     |
| `tool_result` | в `toolActivity` записывается результат                                                                     |
| `text_delta`  | дописывается `content`, статус сообщения `streaming`, подпись «Формирую ответ» |

`toolActivity` хранится и в `generations` (живое состояние), и в самом сообщении — поэтому результат инструмента не пропадает после завершения стриминга и переживает перезагрузку.

### Защита от устаревших событий

Каждое событие несёт `requestId`. Редьюсер применяет его, только если он совпадает с `requestId` текущей генерации этого чата. Если чат удалён или запущена новая генерация, «опоздавшие» события, `fulfilled` и `rejected` игнорируются. Это покрыто тестами.

## 7. Мок-агент (`mockAgent.ts`)

`streamAgentReply(request, signal)` — асинхронный генератор типизированных событий `AgentEvent`:
`started`, `status`, `tool_call`, `tool_result`, `text_delta`, `completed`, `error`.

- Вход: `{ prompt, history }` — история нужна для контекстного ответа.
- Задержки: 420 мс «обработки», 32 мс на кусок текста; у калькулятора дополнительные паузы.
- Текст режется на слова (`\S+\s*`), каждое слово — событие `text_delta`.
- `AbortSignal` прерывает ожидание (`wait` отклоняется с `AbortError`).
- Модуль ничего не знает о React и Redux, поэтому тестируется отдельно, и его можно заменить реальным API, сохранив контракт событий.

### 7.1. Подробный разбор `mockAgent.ts`

Файл читается сверху вниз: типы → константы → вспомогательные функции → главный генератор `streamAgentReply` в конце.

#### Типы

- `AgentEvent` — объединение с дискриминатором `type`. Благодаря этому TypeScript в редьюсере (`switch (event.type)`) знает, какие поля есть у каждого события: у `status` — `message`, у `tool_call` — `tool`, у `tool_result` — `tool` и `result`, у `text_delta` — `text`, у `error` — `message`; `started` и `completed` без данных.
- `AgentRequest` — вход агента: `prompt` (текст пользователя) и `history` (все сообщения чата, `ChatMessage[]`). История нужна только для контекстных ответов.

#### Константы

- `PROCESSING_DELAY_MS = 420` — «думание» перед любым ответом.
- `STREAM_DELAY_MS = 32` — пауза перед каждым куском текста; именно она создаёт эффект печати.

#### `wait(delay, signal)` — отменяемая пауза

Возвращает промис, который выполняется через `delay` мс.
1. Если сигнал уже отменён, сразу отклоняется с `DOMException('AbortError')`.
2. Иначе ставится `setTimeout`, а на `signal` вешается слушатель `abort` (`{ once: true }`).
3. По таймеру слушатель снимается и промис выполняется. При отмене таймер очищается и промис отклоняется с `AbortError`.

Так любая пауза в агенте мгновенно прерывается без «висящих» таймеров. Ошибка `AbortError` проходит наружу через генератор к вызывающему коду.

#### `getPreviousAssistantMessage(history)`

Копирует историю, переворачивает и ищет первое сообщение с `role === 'assistant'` и `status === 'complete'`, то есть последний успешно завершённый ответ. Прерванные и ошибочные ответы игнорируются. Копия (`[...history]`) нужна, чтобы `reverse()` не изменил исходный массив.

#### `createReply({ prompt, history })` — выбор текста ответа

Проверки идут строго по порядку, срабатывает первая подходящая (регистр не важен, флаг `i`):
1. **Контекстное «проще»**: в запросе есть `проще | попроще | короче | по-другому | другими словами` **и** в истории есть завершённый ответ ассистента. Если тот ответ содержал «закон Ома», возвращается упрощённая аналогия про ток и сопротивление. Иначе — «Конечно, объясню проще. Главная мысль предыдущего ответа: …» с цитатой прошлого ответа. Это сценарий, учитывающий предыдущие сообщения чата.
2. **Закон Ома** (`закон ома`): формула `I = U / R` и аналогия с водой в трубе.
3. **Второй закон Ньютона**: формула `F = m × a`.
4. **Решение задачи** (`реши/решить/решение … задач`, `не давай ответ`, `с подсказк…`): предлагает идти по шагам, без готового ответа.
5. **Запасной вариант**: подставляет запрос пользователя в шаблон и просит уточнить, что кажется сложным.

#### `calculate(prompt)` — разбор арифметики

- Регулярное выражение ищет `число оператор число`: числа с необязательным минусом и десятичной частью через точку или запятую, оператор из `+ * × x / ÷ -`.
- Запятая заменяется на точку, затем строки превращаются в числа (`Number`). Оператор приводится к нижнему регистру, поэтому `X` тоже работает.
- `switch` по оператору считает результат; для неизвестного оператора есть `default: return null` (нужен для проверки типов: переменная `result` обязана быть инициализирована).
- Если результат не конечное число (например, деление на ноль даёт `Infinity`), возвращается `null`, и запрос обрабатывается как обычный текст.
- При успехе возвращается `{ expression, result }`, где `expression` — найденная подстрока (`17 × 24`), без пробелов по краям.

Особенность: поиск идёт по всему тексту, поэтому любое подходящее выражение внутри фразы (даже дата вида `2024-05`) будет принято за вычисление. Для учебного мока это допустимо.

#### `formatNumber(value)`

`Intl.NumberFormat('ru-RU', { maximumFractionDigits: 4 })`: русские разделители (`408`, `0,3333`, `1 000`), не более четырёх знаков после запятой.

#### `streamText(text, signal)` — стриминг текста

Вложенный асинхронный генератор.
1. Режет текст на куски регулярным выражением `/\S+\s*|\s+/g`: слово вместе с пробелами после него (либо отдельный блок пробелов). Если совпадений нет, используется весь текст целиком.
2. Для каждого куска ждёт `STREAM_DELAY_MS` (через `wait`, то есть с поддержкой отмены) и отдаёт `{ type: 'text_delta', text: chunk }`.

Склеив все `text`, получаем исходный текст без потерь.

#### `streamAgentReply(request, signal)` — главный генератор

`async function*` — функция, которая выдаёт события по одному через `yield`, а потребитель читает их циклом `for await`. Генератор «ленивый»: код выполняется до очередного `yield`, затем ждёт, пока потребитель запросит следующее событие.

Порядок работы:
1. `yield { type: 'started' }` и пауза 420 мс.
2. **Ветка ошибки.** Если запрос содержит `вызови ошибку | смоделируй ошибку | ошибка агента`, выдаётся `{ type: 'error', message: 'Не удалось подготовить ответ…' }` и генератор завершается через `return`. События `completed` в этом случае нет.
3. **Вызов `calculate`.**
   - Если выражение найдено, выдаётся последовательность: `status` «Использую калькулятор» → пауза 240 мс → `tool_call` («Калькулятор») → пауза 180 мс → `tool_result` (например, `17 × 24 = 408`) → `status` «Готовлю объяснение». Текст ответа: «Посчитаем по шагам: … Ответ: …».
   - Если нет, выдаётся `status` «Готовлю объяснение», а текст берётся из `createReply`.
4. Текст отдаётся через `for await (const event of streamText(reply, signal)) yield event` — события вложенного генератора пересылаются наружу.
5. В конце `yield { type: 'completed' }`.

Приоритет таким образом: **ошибка → калькулятор → остальные сценарии**. Поэтому запрос «объясни проще, сколько будет 2+2» обработается калькулятором.

#### Пример последовательности событий

Запрос «Сколько будет 17 × 24?»:

```
started → (420 мс) → status «Использую калькулятор» → (240 мс) →
tool_call «Калькулятор» → (180 мс) →
tool_result «17 × 24 = 408» → status «Готовлю объяснение» →
text_delta ×N (по одному на слово, каждые 32 мс) → completed
```

#### Как агент используется снаружи

Его вызывает thunk `runAssistant` в `chatsSlice.ts`: передаёт `{ prompt, history }` и `AbortSignal`, читает события через `for await` и диспатчит каждое как `agentEventReceived`. Сам агент ничего не знает о Redux, React и `localStorage`, поэтому тесты в `mockAgent.test.ts` просто собирают события в массив и проверяют их.

## 8. Сохранение (`chatPersistence.ts`, `store.ts`)

- Ключ `lom-ai-chat-state`, сохраняется `{ conversations, activeConversationId }`.
- Запись идёт через listener middleware на `createConversation`, `selectConversation`, `deleteConversation` и жизненный цикл `runAssistant` (pending/fulfilled/rejected). Каждый `text_delta` не пишется — это экономит запись.
- При загрузке структура валидируется; повреждённые данные игнорируются. Недоступный `localStorage` или ошибка записи показывают предупреждение (`persistenceWarning`).
- Сообщения со статусом `processing`/`streaming` после перезагрузки становятся `error` с текстом «Ответ прервался при перезагрузке. Можно попробовать ещё раз.»

## 9. Интерфейс

- **Адаптив.** Брейкпоинт 760 px: на мобильных сайдбар выезжает с затемнением; есть правило и для широких экранов от 1500 px.
- **Тач-устройства.** Кнопка удаления видна всегда (`@media (hover: none)`), на десктопе — при наведении.
- **Доступность.** Список сообщений — `role="log"`, у индикаторов есть `aria-label`, управление с клавиатуры, `prefers-reduced-motion` отключает анимации.
- **Длинные сообщения** переносятся и не ломают вёрстку (проверено на 1440 и 390 px).

### 9.1. Главный компонент `App.tsx`

`App.tsx` — корневой компонент приложения. Он не содержит всю бизнес-логику чата внутри себя, а связывает Redux-состояние с визуальными компонентами: боковой панелью диалогов, областью сообщений и полем ввода.

#### Импорты и локальное состояние

В начале файла импортируются:

- `useState` из React — для локального состояния открытия боковой панели на мобильных экранах;
- `useAppDispatch` и `useAppSelector` — типизированные хуки Redux;
- actions из `chatsSlice` — создание, выбор и удаление диалога, запуск ответа ассистента и закрытие предупреждения;
- типы `Conversation` и `UserMessage`;
- компоненты `ConversationSidebar`, `ChatView` и `MessageComposer`;
- `App.css` со стилями оболочки приложения.

```tsx
const [isSidebarOpen, setIsSidebarOpen] = useState(false)
```

Состояние `isSidebarOpen` не нужно хранить в Redux: оно относится только к отображению текущего компонента. История чатов и состояние генерации, наоборот, являются общими данными и читаются из Redux:

```tsx
const {
  conversations,
  activeConversationId,
  generations,
  persistenceWarning,
} = useAppSelector((state) => state.chats)
```

Затем компонент находит активный диалог и его текущую генерацию:

```tsx
const activeConversation = conversations.find(
  ({ id }) => id === activeConversationId,
)
const activeGeneration = activeConversation
  ? generations[activeConversation.id]
  : undefined
```

Если активного диалога нет, `activeConversation` равен `undefined`, а `ChatView` получает пустой список сообщений. Если для диалога идёт генерация, `activeGeneration` содержит её статус и компоненты блокируют повторную отправку.

#### Создание диалога

`handleCreateConversation` создаёт объект `Conversation` с уникальным ID, датами и пустой историей сообщений:

```tsx
const now = new Date().toISOString()
const conversation: Conversation = {
  id: createId(),
  title: 'Новый диалог',
  createdAt: now,
  updatedAt: now,
  messages: [],
}
```

После этого action `createConversation` передаётся в Redux через `dispatch`. Боковая панель закрывается, чтобы на мобильном экране пользователь сразу увидел чат.

#### Отправка сообщения

`handleSendMessage` получает текст из `MessageComposer`. Сначала он проверяет, не генерируется ли уже ответ:

```tsx
if (activeGeneration) {
  return
}
```

Если активного диалога ещё нет, функция автоматически создаёт новый. Это позволяет отправить первое сообщение сразу, не заставляя пользователя сначала нажимать «Новый диалог».

Далее создаётся типизированное пользовательское сообщение с уникальным ID и временем отправки. Action `runAssistant` получает ID диалога, пользовательское сообщение и новый ID сообщения ассистента. Thunk добавляет сообщение и запускает поток событий от локального mock-агента; подробности его работы описаны в разделе про `chatsSlice.ts`.

#### Повторная попытка

`handleRetry` вызывается из `ChatView` после ошибки. Он проверяет наличие активного диалога и отсутствие другой генерации, затем снова запускает `runAssistant` для исходного пользовательского сообщения:

```tsx
dispatch(
  runAssistant({
    conversationId: activeConversation.id,
    userMessageId,
    assistantMessageId: createId(),
    assistantCreatedAt: new Date().toISOString(),
  }),
)
```

Создаётся новый ID сообщения ассистента, поэтому повторная попытка не использует случайно устаревшее состояние предыдущего ответа.

#### Переключение и удаление диалогов

`handleSelectConversation` отправляет action `selectConversation`, а затем закрывает мобильную боковую панель. Redux меняет `activeConversationId`, после чего компонент автоматически перерисовывается с историей выбранного диалога.

`handleDeleteConversation` сначала показывает пользователю `window.confirm`. Удаление выполняется только после подтверждения:

```tsx
if (confirmed) {
  dispatch(deleteConversation(conversation.id))
}
```

Само удаление, выбор другого диалога и очистка состояния генерации выполняются в slice, чтобы одинаково работать из любого места приложения.

#### JSX-структура

Корневой JSX состоит из двух основных частей:

1. `ConversationSidebar` — список диалогов, создание, выбор и удаление;
2. `main.chat-panel` — заголовок, предупреждение о сохранении, сообщения и поле ввода.

В заголовке статус зависит от `activeGeneration`:

```tsx
{activeGeneration?.statusText ?? 'Всегда готов помочь'}
```

Когда генерация активна, к индикатору добавляется CSS-класс `status-dot--busy`.

Предупреждение `persistenceWarning` отображается только при наличии текста. Кнопка закрытия отправляет `setPersistenceWarning(null)`, поэтому предупреждение исчезает из интерфейса и из Redux-состояния.

`ChatView` получает сообщения только активного диалога:

```tsx
messages={activeConversation?.messages ?? []}
```

Оператор `?.` безопасно обрабатывает отсутствие диалога, а `?? []` передаёт пустой массив вместо `undefined`. В `disabled` передаётся `Boolean(activeGeneration)`, поэтому при потоковой генерации повторный ввод и отправка блокируются.

`MessageComposer` использует тот же обработчик `handleSendMessage`, что и быстрые подсказки в `ChatView`. Благодаря этому обычная отправка и отправка по подсказке проходят через единый сценарий.

Итого, `App.tsx` выполняет роль координатора:

```text
действие пользователя
        ↓
обработчик App.tsx
        ↓
dispatch Redux action
        ↓
обновление состояния chats
        ↓
перерисовка ChatView, Sidebar и Composer
```

Компонент не вычисляет ответы агента и не управляет отдельными сообщениями напрямую. Он передаёт команды в Redux и получает из Redux данные, необходимые для отображения текущего интерфейса.

#### Переключение темы

`App.tsx` также управляет локальным состоянием темы интерфейса:

```tsx
const [theme, setTheme] = useState<Theme>(getInitialTheme)
```

Поддерживаются два значения: `light` и `dark`. Начальное значение читается из `localStorage`, а `useEffect` записывает выбранную тему в `data-theme` корневого HTML-элемента:

```tsx
document.documentElement.dataset.theme = theme
```

Кнопка в шапке переключает тему и сообщает текущее действие через `aria-label` и `aria-pressed`. Цвета компонентов не меняются в React-коде: `index.css` задаёт CSS-переменные для обеих палитр, а `App.css` добавляет тёмные состояния для карточек, сообщений, поля ввода и интерактивных элементов. Поэтому переключение темы не затрагивает Redux-состояние, историю чатов или процесс генерации ответа.

## 11. Возможные вопросы на интервью

- **Почему Redux Toolkit?** Состояние общее для сайдбара, чата и композера, есть сложный жизненный цикл (асинхронные генерации по нескольким чатам), нужны предсказуемые редьюсеры и удобное тестирование.
- **Почему агент вынесен в отдельный модуль?** Изоляция от UI и стора, независимое тестирование, возможность заменить на реальный API без правки компонентов.
- **Как избегаете гонок?** `requestId` у каждой генерации, проверка в редьюсерах, `condition` у thunk-а, очистка `generations` при удалении чата.
- **Почему стриминг не сохраняется на каждый chunk?** Лишние записи в `localStorage`; достаточно сохранять на границах жизненного цикла, а прерванный ответ восстанавливается как ошибка с повтором.
- **Как показан tool use?** События `tool_call`/`tool_result`, карточка в сообщении, результат хранится в сообщении.
- **Как масштабировать?** Реальный API через ту же схему событий (SSE/fetch streaming), `AbortController` для отмены, тесты компонентов и e2e.

## 12. Ограничения

- Агент работает по шаблонам, а не понимает язык.
- Нет кнопки остановки генерации и редактирования сообщений.
- Нет тестов компонентов и e2e; проверка интерфейса выполнялась вручную в браузере.
- Данные хранятся только в `localStorage` конкретного браузера.
